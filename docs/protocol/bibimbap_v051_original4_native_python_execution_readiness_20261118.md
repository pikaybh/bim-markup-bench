This is research on original public BIBIMBAP source IFC4X3/mm files, **not** a BIXML product change, not a 45-task model trial, and not a paid LLM run. The primary causal comparison remains **D-state declarative XML before/after editing** versus **I-native actually executed Python/IfcOpenShell editing**. v0.47's AST-only typed Python call is auxiliary T-Python and **not** this I-native arm.

## Already implemented and independently checked

A separate v0.51 model-facing session in tools/bibimbap_v051_executed_original_native_python_session.py offers two tools, both bounded by a combined 25 tool calls. **read_building_xml** returns exactly the same initial source XML UTF-8 bytes as the independent v0.50 D-state read tool, including complete original IFC native STEP, GUIDs, source world physical geometry, materials, local placements, original relations, source native schema and units, and the explicit original managed object state. **execute_ifc_code** accepts **general Python code**, rather than an AST-only whitelisted command, passing it to the already existing local DockerIFCExecutor / bibimbap_docker_ifc_code_worker.py worker. The actual production worker exports ifc (a loaded ifcopenshell.file), ifcopenshell, api, util, element_util, guid, result and commit(). It does not directly expose scorer/GT/positive developer control files. An I-arm model may edit the actual native IFC using arbitrary normal IfcOpenShell APIs inside the sandbox, and must request commit. It never submits XML editing opcodes.

The host does not accept even a successful worker commit as valid until the **new independent original-native I-arm physical source oracle** in tools/bibimbap_v051_independent_native_python_oracle.py passes. This verifier reads actual IFC4X3/mm source and candidate *without D XML plan, D compiler, typed v0.45 mutation and without original author grader*. It checks original source SHA, original task identity and known inventory; original and output IFC schema/length-unit, STEP envelope, surviving IfcRoot classes/names/descriptions, new or missing root GUIDs, allowed deletion cascade only, exact surviving relationship endpoint roles, original surviving native property/unit/material entities, all source physical product meshes, unchanged non-target geometry, exact task-bounded edit geometry and placement constraints, and actual non-no-op change. It uses existing independently implemented low-level IFC mesh and source relation helpers, but does **not** consume an expected NativeEditPlan. It intentionally accepts physically valid yet **task-wrong** edit candidates and leaves the separate source/author task semantic judgement to an external evaluator.

Candidate IFC writing is staged in a fresh per-call scratch directory as a clone of last independently approved IFC. Only a worker response with status ok, explicit commit() and a physically valid independently verified candidate can replace the session's last-valid result. Exceptions, worker failures after commit, no-ops, ill-formed STEP, forged new IfcRoot, scope violations and wrong native metadata fail without replacing the original or last-good candidate. The initial original source file never enters the model-visible mounted folder; only an expendable original source clone resides there.

## Source/authority fairness and unresolved token costs

- D-state and I-native receive **identical initial source XML bytes**, independently verified for all four originally selected IFC source hashes. This is stronger than the v0.47 comparison's Python literal escaping. Both have 25 total tool calls and one initial read tool. Model prompts and tokenized tool schemas still differ: D submits complete edited XML and gets compiler/oracle feedback, I submits executable source code and gets sandbox stdout/result/oracle feedback. **Equal initial bytes are not proof of equal provider token consumption, equivalent edit-space expressiveness, equal debugging affordances, equal wall time or matched prompt length.**
- Exact four source public tasks: geometry_test_14 (Slab rectangle increase), geometry_test_15 (one Column move), topological_test_11 (mapped shared Column extrusion), topological_test_17 (delete 1–9 original Columns); 45 original questions / 31 native IFC sources unchanged. The other 41 original task rows were not attempted. Original data/question/GT/scorer and prior v0.50 report SHA remain unmodified. Four previously chosen tasks are exploratory, not a prospectively randomized sample.
- No external provider/model inference was performed; provider snapshot, actual input/output token usage, model error/attempt rates and author grader scores remain **NULL**. No claim of D-vs-I causal effect.

## Docker runtime admission and security

Existing research Docker executor uses digest pinned to sha256:2ce0d57dff6ea443c7f5ffffd29cf8b1b50a141b77574aae5ca4646f45f3a1ee (not an unpinned tag), with a fixed platform-local endpoint. On Windows, exact endpoint is npipe:////./pipe/dockerDesktopLinuxEngine; network=none, read-only rootfs, capability drop ALL, no-new-privileges, non-root uid/gid 65534, memory 768 MiB, one CPU, 32 PIDs, tmpfs, only two mounts (disposable workspace read/write and worker Python file read-only). The executor attests the created Docker container's actual HostConfig and exact image digest before executing a submitted Python snippet.

v0.51 adds an explicit **read-only runtime admission** before any execute_ifc_code call. It checks the fixed local engine's Linux OSType via Docker CLI and locally inspects the exact already-pinned image SHA without downloading, building or starting Docker. When engine or image is not available, the model-facing host returns BLOCKED_RUNTIME and **does not execute code, create an attempt, or claim I-arm success**. On the connected Windows PC the Docker CLI is installed (28.3.2), but the Docker Desktop Linux engine pipe is missing (no Docker engine process). Do not change daemon lifecycle from a research run or automatically use another server/context. Any future real model-authored Python execution requires the local pinned daemon/image and a separate live sandbox attestation.

## Offline developer physical controls (NOT real model executions)

The developer-only tools/bibimbap_v051_trusted_developer_python_controls.py executes **eight independent, trusted Python/IfcOpenShell editing control fixtures on the Windows research host**. These do not use the D-state diff compiler or v0.45 NativeEditPlan. The fixtures derive physical control target states only from original **public** questions + source IFC geometry/storey containment and never from private GT/author scorer. Four correct research physical controls and four intentionally wrong-but-physically-valid edits were produced as new real native IFC4X3/mm files. For each, new v0.51 native scope oracle independently passed, and the separate v0.48 source-native task physical research oracle passed on the four positives and rejected the four negatives. This is **not** an official author benchmark score or real LLM outcome. Candidate source SHA/provenance are stored without target GUIDs, hidden answers, or developer solution patch text in the frozen report.

An explicit **offline copied-IFC test double** exercises the I-native session commit boundary, successful native oracle, failure/rollback and original-source preservation using these trusted developer native IFC files. Even if that double returns a forged "linux_docker_sandbox" backend field, the v0.51 host marks python_execution_attested=false and offline_test_double_not_real_python=true. It is never counted as a real model-authored Python run. This prevents a disconnected local Docker runtime from being falsely represented as a real I-arm success.
